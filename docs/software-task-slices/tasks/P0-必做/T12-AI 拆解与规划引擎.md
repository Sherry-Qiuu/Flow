# T12 · AI 拆解与规划引擎

> 工作流：**任务与规划**（TASK）・优先级 **P0**・规模 **L**（4 人日）

| 字段 | 内容 |
|---|---|
| 任务 ID | `T12` |
| 工作流 | 任务与规划（`TASK`） |
| 优先级 | P0 |
| 规模 | L / 4 人日 |
| 前置依赖 | `T10` |
| 需协同 | `T11`、`T13`、`T14`、`T27` |
| 建议角色 | AI / 后端 |

## 1. 目标

产品真正的护城河：把“写 3000 字论文”拆成“现在打开文档列 3 个论点”，并排进可执行的日程。

## 2. 需求依据

- **SR-03** — 计划表（将大任务拆分，细化可现在落实）直接输出显示在屏幕上（P19）
- **SR-03** — 解决现在市面上大多效率 App 只有大目标任务、没有从 0 到 1 下手点的问题（P27）
- **SR-03** — 把大任务拆小 + 提前提醒，消除“遗忘恐惧”和“不知从哪开始”的启动焦虑（P26）

## 3. 输入 / 输出

**输入**

- T10 任务与用户偏好
- LLM API（DeepSeek / Qwen 等 OpenAI 兼容接口）

**输出（可交付物）**

- decompose(task) -> subtasks
- plan(date, tasks, prefs) -> PlanDraft
- 规则引擎降级实现
- 校验器与可解释理由

## 4. 工作内容

- [ ] 拆解：LLM + JSON Schema 强约束，每任务拆 3–7 步，单步 15–45 分钟
- [ ] 拆解准则写进 prompt：以动词开头、可独立完成、有明确完成判据、第一步 ≤ 20 分钟
- [ ] 时间估算：有历史数据时用同类任务实际耗时，无数据时按规则表（阅读/写作/背诵/实验/讨论）
- [ ] 排期：可用时段装箱，考虑截止时间（EDF）、精力曲线（上午难任务 / 晚间轻任务）、20% 缓冲、每 45–50 分钟插休息
- [ ] 依赖：支持任务间前置关系，前置未完成不能开始
- [ ] 一致性校验：不超期、不重叠、总时长 ≤ 可用时间；不满足时削峰并主动告知用户
- [ ] 降级：LLM 不可用 → 规则引擎（模板拆解 + 均分时长），保证永远能出计划
- [ ] 可解释：每处调整给一句话理由（“因为周三有实验，把预习放到周二晚”）
- [ ] 成本控制：同一任务文本 24 小时内复用结果；批量任务一次调用完成拆解

## 5. 接口契约

```
def decompose(task: Task, prefs: Prefs) -> list[SubTask]

def plan(plan_date: date, tasks: list[Task], prefs: Prefs) -> PlanDraft

PlanDraft = {
  "plan_id": "p_20261108",
  "date": "2026-11-08",
  "items": [{"task_id": "...", "subtask_id": "...", "start": "19:00", "end": "19:30",
             "title": "列出论文 3 个核心论点", "est_minutes": 30}],
  "breaks": [{"start": "19:30", "minutes": 10}],
  "notes": [{"text": "周三有实验，预习挪到周二晚", "ref": "task_id"}],
  "warnings": []
}
```

## 6. 验收标准（Definition of Done）

- [ ] 输入 5 条杂乱任务，输出计划无时间重叠、无超期、总时长不超可用时段
- [ ] 每一步时长 ≤ 45 分钟且以动词开头（机器校验，抽查 20 条）
- [ ] 首次打开能把“写 3000 字论文”拆到“打开文档列出 3 个论点”这种颗粒度
- [ ] 断网 / LLM 超时时仍能在 3 秒内产出可用计划（规则引擎）
- [ ] 单次规划 P95 延迟 ≤ 8 秒
- [ ] 校验器能稳定拦截人为注入的重叠与超期计划

## 7. 风险与降级

- LLM 拆得太细导致步骤爆炸 → 硬性限制 7 步，超出则合并
- 估算偏乐观导致永远做不完 → 用实际耗时做滚动校准（实际/预估的中位数比值）
- API 费用 → 缓存 + 小模型做粗拆 + 大模型只做难任务
