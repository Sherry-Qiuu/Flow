## 1. 目标

让用户看得懂、改得动、愿意签的计划表——这是“商量”真正发生的地方。

## 2. 需求依据

- **SR-04** — 和用户进行商讨后指定最终版计划表（P19）
- **SR-05** — 开始执行计划的时候屏幕上极简显示步骤（P19）

## 3. 输入 / 输出

**输入**

- T12 PlanDraft
- T05 设计系统
- T08 对话动作

**输出（可交付物）**

- PlanReview 页面（时间轴 + 列表双视图）
- 语音/手势修改流程
- 冲突检测提示与版本撤销

## 4. 工作内容

- [ ] 双视图：纵向 24h 时间轴（默认）与紧凑列表，语音可切换
- [ ] 每项显示：时间、任务名、当前步骤、预计时长、来源标记（新任务 / 已有任务）
- [ ] 修改通道：语音（“把英语挪到下午”）、手势（挥手确认 / 下一个）、必要时逐项语音确认
- [ ] 冲突提示：修改造成重叠时高亮并给出建议（“往后推 20 分钟”），不允许静默重叠
- [ ] 汇总条：总时长、最晚结束时间、休息次数、预估完成率
- [ ] 确认 → 发 plan.confirmed 进执行态；“再改改” → 回到对话并保留草稿
- [ ] 版本：保留上一版，一句话“撤回到上一版”即可回滚
- [ ] 可读性：10 项以内一屏可读完，超出自动分页但不打断语流

## 5. 子任务拆解

每项 ≤0.5 人日，可单独勾选验收。做完一项就在 `产物` 那一列把文件建出来。

| 子任务 | 名称 | 产物 | 完成判据 | 人日 |
|---|---|---|---|---|
| `T13.1` | 时间轴 / 列表双视图 | `ui/src/pages/PlanReview/*` | 10 项以内一屏读完；正文 ≥28px；可语音切换视图 | 0.75 |
| `T13.2` | 语音与手势修改 | `POST /api/plan/{id}/revise + ui 刷新` | “把英语挪到下午” 后 2 秒内界面更新 | 0.5 |
| `T13.3` | 冲突提示与汇总条 | `ui/src/pages/PlanReview/Conflict.tsx` | 重叠/超期必被显式提示并给建议；汇总显示总时长与最晚结束 | 0.25 |
| `T13.4` | 确认、撤销与版本 | `POST /api/plan/{id}/{confirm,undo}` | 确认后首步立即可见；撤销准确回到上一版 | 0.5 |

**小计 2.00 人日**

## 6. 接口契约

```
# 事件：plan.draft / plan.confirmed / plan.revised
# REST：POST /api/plan/{plan_id}/revise {"instruction": "把英语挪到下午"}
#       POST /api/plan/{plan_id}/confirm
#       POST /api/plan/{plan_id}/undo
```

## 7. 实现要点

```
POST /api/plan/{plan_id}/revise  {"instruction": "把英语挪到下午"}
POST /api/plan/{plan_id}/confirm
POST /api/plan/{plan_id}/undo

revise 内部：
    旧稿 = repo.plans.get(plan_id)
    acts = dialogue.parse(instruction)      # 复用 T08
    新稿 = planner.modify(旧稿, acts)
    issues = validate_plan(新稿)            # 复用 T12 校验器
    若 issues 有 error → 返回冲突 + 建议，不落库
    否则存版本并广播 plan.revised
```

## 8. 验收标准（Definition of Done）

- [ ] 10 项以内的计划在一屏内可读完，正文 ≥ 28px
- [ ] 语音修改后 2 秒内界面刷新并显示新的时间安排
- [ ] 确认后进入执行态，第一个步骤立即可见
- [ ] 任何重叠/超期都被显式提示，不会静默通过
- [ ] 撤销操作能准确回到上一版计划

## 9. 风险与降级

- 无触屏导致修改路径不直观 → 每屏给一句“你可以说……”的提示语，引导而非依赖发现
- 计划项过多时信息密度过高 → 默认折叠未开始项，只展开当前时段

## 10. 提示

> 把“不好意思，我改一下”做成正常流程而不是错误流程。协商是卖点，不是失败。
