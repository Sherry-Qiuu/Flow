# T25 · 数据隔离与个性化偏好

> 工作流：**账号与多用户**（USR）・优先级 **P1**・规模 **M**（2 人日）

| 字段 | 内容 |
|---|---|
| 任务 ID | `T25` |
| 工作流 | 账号与多用户（`USR`） |
| 优先级 | P1 |
| 规模 | M / 2 人日 |
| 前置依赖 | `T10`、`T24` |
| 需协同 | `T07`、`T12`、`T26` |
| 建议角色 | 后端 |

## 1. 目标

保证多用户下“数据不串、偏好不混”，并且每个人看到的产品真的不一样。

## 2. 需求依据

- **SR-21** — 多用户为追加需求；个性化服务于“减少认知负荷”的产品目标。

## 3. 输入 / 输出

**输入**

- T24 用户体系
- T10 DAO

**输出（可交付物）**

- 强隔离的 DAO 约束
- 偏好模型（作息、音色、静音、语气、娱乐上限）
- 导出 / 删除接口

## 4. 工作内容

- [ ] 所有查询强制 user_id 过滤；DAO 层加断言：没有 user_id 直接抛异常（把错误提前到开发期）
- [ ] 偏好表：作息时段（早起型/夜猫型）、喜欢的音色、静音时间、提醒语气、娱乐时长上限、主题色
- [ ] 个性化落地：规划引擎按作息排期、TTS 按偏好选音色、庆祝文案按风格选择
- [ ] 数据导出：单个用户一键导出 JSON（任务、计划、会话、统计）
- [ ] 数据删除：一键删除且级联清理（含事件表与缓存）
- [ ] 隔离测试：写跨用户读取用例，必须 0 泄漏

## 6. 验收标准（Definition of Done）

- [ ] 单测覆盖“以 A 身份读 B 的数据”必须失败（至少 10 个用例）
- [ ] 导出的 JSON 包含该用户全部数据且可被重新导入
- [ ] 删除后数据库中无任何残留（含 device_events 与缓存）
- [ ] 偏好修改后在计划排期与语音音色上可观察到差异

## 7. 风险与降级

- 个性化做太深导致调试困难 → 只做 4–5 个真正影响体验的偏好

## 8. 提示

> 把 user_id 做成服务端的隐式上下文（中间件注入），而不是每个函数都手动传参——手动传参迟早会漏。
