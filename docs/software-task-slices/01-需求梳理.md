# 01 · 软件需求梳理

把 [产品设计.docx](产品设计.docx) 里的每一段描述，翻译成软件需要做的事。**这是“要做什么”的唯一依据**，任务卡里的 `SR-xx` 都指回这里。

## 从产品定位推导出的软件命题

| 产品原文 | 翻译成软件要求 |
|---|---|
| 任务积压 → 失控感 → 回避拖延 → 积压更严重（P10） | 系统必须能在**任意时刻**回答“现在该做什么”，而不是给一张越来越长的清单 |
| 单通道强制聚焦，降低过载（P16） | 需要一套**强制单焦点**的界面与状态机，不能靠用户自律 |
| 市面上 App 只有大目标、没有 0→1 下手点（P27） | **拆解引擎是核心差异点**，不是附属功能 |
| 多人协作 / 一台设备放宿舍（隐含） | 从第一版起数据模型就要带 `user_id` |
| 实体设备，14×14 屏、无触屏（P38–P43） | 交互只能靠**语音 + 手势 + 传感器**，界面为“读”而非“点”设计 |

## 优先级口径

- **P0**：去掉它产品就不成立，或演示主线断掉。必须做。
- **P1**：定义里的体验加分项，影响“好不好用”。有余力就做。
- **P2**：增强与长期演进，可以留到下一版。

## 现成 App 做不到什么（差异点清单）

做评审或答辩时，这几条是最容易被追问的，提前准备：

1. **只给目标不给第一步。** 待办类 App 记的是“写论文”，本产品输出的是“打开文档列出 3 个论点（20 分钟）”。
2. **信息越多越焦虑。** 本产品主动做减法：任意时刻只呈现一个通道。
3. **提醒是打扰，陪伴是支撑。** 提醒之外还有完成反馈、养成、主动建议休息。
4. **不评判。** 分心数据只用于“让你更了解自己”，不生成欠账和红叉。
5. **物理在场。** 手机要么在架子上、要么在约定期限内使用，注意力外流被物理化地管理。

## 文档里没写、但实现时必须补的需求

这些原文没提，但不解决就做不下去，已作为 `SR-21` / `SR-22` 纳入：

- **时间基准**：所有提醒、排期依赖准确的系统时间（NTP + 断电恢复）。
- **数据持久化**：断电不可丢，否则用户第二天会发现自己白干了。
- **多用户与隔离**：一台设备多人用，任务、计划、提醒、画像必须互不可见。
- **隐私**：分心与手机使用数据极其敏感，必须本地存储、可关闭、不上传。
- **降级**：断网、断摄像头、断麦克风时产品要能用，不能变成砖头。
